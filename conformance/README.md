# Conformance material

Shared by the Java and the TypeScript tests, so that both sides are checked against the same thing.

## `evaluation/`: the two evaluators must agree

The service's evaluator (`TrustEvaluator.java`) is the reference for trust decisions; the client library
(`LocalEvaluator`) must reach the same ones from the snapshot.

- `cases.json` is written by hand: a registry (entities and anchors, as an operator would list them) and queries.
  Strings ending in `pem:NAME`, `pki:NAME` (base64 DER), `crl:NAME`, `sha256:NAME`, `aki:NAME` and `subject:NAME`
  refer to `pki/NAME`.
- `vectors.json` is generated from it by the service (`EvaluationVectorsTest`): the snapshot it signs for a lenient
  and a strict client, and for every query the outcome of its own evaluation: decision, error and warning codes,
  entity, path validation result with each certificate's revocation status, `trusted_authorities` matches.

```sh
cd trust-server
mvn test -Dtest=EvaluationVectorsTest -Dsurefire.failIfNoSpecifiedTests=false                          # fails when vectors.json is stale
mvn test -Dtest=EvaluationVectorsTest -Dsurefire.failIfNoSpecifiedTests=false -Dvectors.update=true    # regenerate
npm test -w @vctrust/trust-client                                                                      # the library must match
```

After a deliberate change to the rules, regenerate and review the diff: every changed line is a change in what
clients are told to trust. A port of the client to another language passes when it reproduces `expect` from
`snapshots`.

## `pki/`: test certificates

A test PKI (an IACA with Document Signers and a CRL, a CA for verifiers and SD-JWT VC issuers, an RSA chain,
self-signed certificates, deliberately wrong certificates), generated by `generate-pki.sh` and `generate-crl.sh`.
The private keys are here because they are test keys; they protect nothing. Two certificates are real, for name
handling: `real-eudi-pid-ca.pem` and `real-waltid-pid-provider.pem` (see `real-world/`).
