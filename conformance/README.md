# Conformance material

Shared by the Java and the TypeScript tests, so that both sides are checked against the same thing.

## `evaluation/`: the two evaluators must agree

The service's evaluator (`TrustEvaluator.java`) is the reference for trust decisions; the client library
(`LocalEvaluator`) must reach the same ones from the snapshot.

- `cases.json` is written by hand: a registry (entities and anchors, as an operator would list them) and queries.
  Strings ending in `pem:NAME`, `pki:NAME` (base64 DER), `crl:NAME`, `sha256:NAME`, `aki:NAME` and `subject:NAME`
  refer to `pki/NAME`.
- `vectors.json` is generated from it by the service (`EvaluationVectorsTest`): the snapshot it signs for a lenient
  and a strict client, and for every query the outcome of its own evaluation: decision, error and warning codes,
  entity and framework, what the entity was found through, path validation result with each certificate's
  revocation status, and for each `trusted_authorities` query the value that matched.

A second pair covers the operator's trust mechanisms (`trust.mechanisms`, see
[Trust mechanisms](../docs/configuration.md#trust-mechanisms)):

- `mechanisms.cases.json` is written by hand: the registry of `cases.json` with one more anchor (`vec-national-id-ca`,
  in a trust domain of the operator's naming), the mechanisms as an operator writes them (`mechanisms`), and queries.
  A case with `sameAsFirstPair` asks a question of `cases.json` and must be decided as it is there, the mechanism
  aside: the test fails otherwise.
- `mechanisms.vectors.json` is generated from it by the service (`MechanismVectorsTest`), configured with those
  mechanisms: its snapshots are format 5 and carry them in `mechanisms`, and each outcome also names the mechanism
  that governed the query (`mechanism`, null for none).

The first pair is the proof that a service without mechanisms decides exactly as before them: its snapshots are
format 4 without the claim, and no decision names a mechanism.

```sh
cd trust-server
mvn test -Dtest='*VectorsTest' -Dsurefire.failIfNoSpecifiedTests=false                          # fails when either pair is stale
mvn test -Dtest=MechanismVectorsTest -Dsurefire.failIfNoSpecifiedTests=false -Dvectors.update=true   # regenerate one pair
npm test -w @vctrust/trust-client                                                                # the library must match both
```

One kind of reason is compared more loosely: why a certificate path is invalid (`x509.path.*`, named after the PKIX
reasons). The service's validator stops at the first rule it finds broken; a client may report every broken rule. A
client must name the reason the service names, and may name more.

After a deliberate change to the rules, regenerate and review the diff: every changed line is a change in what
clients are told to trust. A port of the client to another language passes when it reproduces `expect` from
`snapshots`.

## `pki/`: test certificates

A test PKI (an IACA with Document Signers and a CRL, a CA for verifiers and SD-JWT VC issuers, an RSA chain, a chain
with an intermediate, self-signed certificates, deliberately wrong certificates and certificates with unusual
subject names), generated by `generate-pki.sh`, `generate-crl.sh`, `generate-chain.sh` and `generate-odd-names.sh`.
`generate-mechanisms.sh` adds the certificates of the mechanism vectors: a national ID CA (`nid-ca`, with an empty
CRL `nid-ca.crl`), a signer under it that meets every member of the vectors' certificate profile (`nid-signer`), one
signer for each member that breaks only that member (`nid-no-ku`, `nid-other-eku`, `nid-foreign`, `nid-long`,
`nid-no-dp`, and `nid-sub-signer` under the intermediate `nid-sub-ca`), a signer without the mDL extended key usage
(`nid-no-mdl-eku`), and a CA certificate presented as a signer under the RSA root (`ca-signer`).
The private keys are here because they are test keys; they protect nothing. Two certificates are real, for name
handling: `real-eudi-pid-ca.pem` and `real-waltid-pid-provider.pem` (see `real-world/`).
